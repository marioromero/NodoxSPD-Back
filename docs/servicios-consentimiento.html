Servicios de Consentimiento

Servicios core del Módulo 2: sellado criptográfico, inmutabilidad del ledger y gestión de consentimientos pendientes.

ProofHashService

Servicio de Sellado Criptográfico

app/Services/Consent/ProofHashService.php

Es el servicio responsable de calcular el proof_hash de cada registro en consent_logs. Este hash es el sello que garantiza la integridad forense del consentimiento: si alguien modifica cualquier campo del registro, el hash deja de coincidir y el fraude es detectable.

Criptografía Core

¿Qué datos sella? El hash se calcula sobre cuatro campos:

  • identifier — email o SHA-256 del RUT del titular
  • policy_hash — SHA-256 del contenido de la política que el usuario aceptó
  • purposes — JSON canónico con los propósitos aceptados/rechazados
  • timestamp — fecha ISO 8601 de cuándo ocurrió el consentimiento

Método compute( ): Toma un payload, lo canonicaliza y devuelve hash('sha256', $canonical).

Canonicalización JSON

El método canonicalize() ordena todas las llaves del payload recursivamente con ksort() antes de serializar a JSON. Esto garantiza que el mismo contenido siempre produzca el mismo hash, independientemente del orden en que se construyó el array en PHP.

// Ejemplo de un payload canonicalizado {
  "identifier": "usuario@email.com",
  "policy_hash": "a1b2c3d4...",
  "purposes": {
    "analytics": true,
    "marketing": false,
    "necessary": true
  },
  "timestamp": "2026-06-26T23:20:11+00:00"
}

Verificación de Integridad

El método computeForLog(ConsentLog $log) reconstruye el payload desde el modelo y recalcula el hash. Para verificar que un registro no ha sido alterado, se compara el hash calculado contra el proof_hash almacenado:

// Verificación manual (ejemplo conceptual)
$esperado = $log->proof_hash;
$calculado = (new ProofHashService())->computeForLog($log);

if ($esperado !== $calculado) {
    // Alguien modificó el registro — alerta forense
}
El proof_hash está almacenado con restricción UNIQUE en la base de datos. Esto no solo evita duplicados accidentales, sino que también es una protección adicional contra manipulaciones.

Inmutabilidad del Ledger

ConsentLog — El modelo que nunca cambia

app/Models/ConsentLog.php

El modelo ConsentLog está diseñado para ser append-only. No se puede modificar ni eliminar un registro una vez creado. Esto es el corazón de la estrategia forense del sistema: cada consentimiento queda congelado en el tiempo.

Ledger Core

Características clave del modelo:

  • $timestamps = false — desactiva los timestamps automáticos de Eloquent. No existe columna updated_at.
  • En el evento creating: asigna recorded_at y created_at manualmente con now()
  • En el evento updating: lanza LogicException — impide cualquier UPDATE
  • En el evento deleting: lanza LogicException — impide cualquier DELETE
  • El campo proof_hash tiene restricción UNIQUE a nivel de BD

Doble Capa de Protección

La inmutabilidad se garantiza en dos niveles:

Capa Mecanismo Qué protege
1. Eloquent Eventos updating y deleting lanzan LogicException Protege contra código que intente modificar registros
2. Base de datos No existe columna updated_at. proof_hash es UNIQUE. Cualquier UPDATE dejaría la fila inconsistente con el hash
Importante: Las excepciones de inmutabilidad son capturadas por el handler centralizado en bootstrap/app.php y devueltas como HTTP 409 con mensaje "No se puede modificar ni eliminar este recurso."
