API Reference — Frontend Módulo 2

Diez endpoints para la integración frontend del Trust Widget: configuración del banner, registro de consentimiento, catálogo de fines legales, generación de enlaces de firma, listado de consents pendientes, bóveda de auditoría, gestión de dominios CORS, personalización visual y Portal Cautivo (consulta + firma).

Base URL: https://api.tudominio.com Formato: JSON · UTF-8 Widget: Público (sin auth) · Panel: Sanctum

Configuración del widget
/api/widget/{company_public_uuid}/config
Propósito / Cuándo se usa

Es el punto de partida del flujo del widget. Se llama una sola vez al cargar la página del sitio de la Pyme, inmediatamente después de que el script widget.js se inicializa. POST
Registrar consentimiento
/api/widget/{company_public_uuid}/consent
Propósito / Cuándo se usa

Se invoca cuando el visitante hace clic en Aceptar, Rechazar o Guardar preferencias. El widget envía los fines aceptados como booleans + timestamp + policy_hash. El ledger consent_logs es inmutable. El endpoint es idempotente: reenvíos del mismo payload retornan 200.

  • Slugs no activos se ignoran silenciosamente.
  • No exponer proof_hash en URL ni en console.log en producción.

GET
Listar consents pendientes
/api/panel/pending-consents
Propósito / Cuándo se usa

Lista los envíos de firma pendientes de la empresa autenticada, ordenados por created_at descendente. Se usa en el panel Angular en la vista "Gestión de Envíos" para mostrar una tabla con todos los PendingConsent registrados, su estado actual y acciones disponibles (re-enviar, ver detalle). POST

/api/panel/pending-consents

Flujo interno
1Frontend envía POST /panel/pending-consents con email + company_policy_id.
↓
2Backend valida email y company_policy_id. Resuelve empresa del usuario autenticado.
↓
3Verifica que la política pertenezca a la empresa y esté published. Si no: 403.
↓
4Genera token criptográfico (64 chars hex). Crea PendingConsent: el mutador cifra el email automáticamente.
↓
5Despacha SendConsentLinkJob a la cola (queue: database). Retorna 201 con id, status, expires_at.
↓
6[Background — Queue Worker] SendConsentLinkJob descifra el email en memoria, construye URL mágica y despacha ConsentLinkMail.
El 201 confirma que el registro se creó y el Job se encoló, no que el correo ya llegó. El envío es asincrónico vía la cola de base de datos. Posibles demoras de segundos a minutos según la carga del worker.
Ejemplo de código (servicio Angular)
Ejemplo ilustrativo, no vinculante a una versión específica de Angular.
sendPortalLink(email: string, companyPolicyId: number): Observable<PortalLinkResponse> {
  return this.http.post<PortalLinkResponse>(
    `${environment.apiUrl}/panel/pending-consents`,
    { email, company_policy_id: companyPolicyId }
  );
}
Notas de implementación
  • El company_policy_id debe obtenerse del listado de políticas publicadas (GET /company/policies?status=published). Solo políticas publicadas son elegibles.
  • No se expone el token ni el PII en la respuesta. Solo id, status y expires_at.
  • El frontend debe implementar feedback visual de loading durante el POST (deshabilitar botón, spinner).
  • Tras éxito (201), mostrar mensaje de confirmación. Opcional: listar enlaces pendientes enviados si se implementa un GET index futuro.
  • Si el email ya tiene un pending activo para esa política, el insert falla por constraint violation (índice único). Manejarlo como 409 en el frontend.
  • Más detalle en Característica F de la Guía Conceptual.

Panel — Bóveda de Auditoría

GET
Bóveda de auditoría
/api/panel/consent-logs
Propósito / Cuándo se usa

Registro inmutable de toda acción de consentimiento realizada por trabajadores y leads: firma (aceptar/rechazar), expiración automática, revocación. Cada registro incluye un proof hash (SHA-256 de 64 caracteres hex) que encadena cada entrada con su predecesora (previous_hash), formando una cadena de integridad tipo blockchain. Se usa en el panel Angular en la vista "Bóveda de Auditoría" para consulta, exportación y verificación forense.

Inmutabilidad: Los registros en consent_logs no pueden ser modificados ni eliminados, ni por el frontend ni por el backend. Solo lectura (GET). Cualquier intento de DELETE/PUT/PATCH devuelve 405 Method Not Allowed.

Notas de implementación
  • Idempotencia: si el token ya fue confirmado, retorna 409 (no 200). El frontend muestra pantalla de "ya firmado".

  • Fines con required=true se fuerzan a true en backend aunque el frontend envíe false (defensa en profundidad).
  • Slugs no activos se ignoran silenciosamente.
  • El proof_hash debe mostrarse al usuario como "Código de recibo de firma" con botón de copiar al portapapeles.
  • Rate limiting: 60 req/min por IP. No spammear reintentos.
