API Reference — Frontend Módulo 2

Tres endpoints críticos para la integración frontend del Trust Widget: configuración del banner, registro de consentimiento y catálogo de fines legales.

Base URL: https://api.tudominio.com Formato: JSON · UTF-8 Widget: Público (sin auth) · Panel: Sanctum

Endpoints

Widget Público

GET
Configuración del widget
/api/widget/{company_public_uuid}/config
Propósito / Cuándo se usa

Es el punto de partida del flujo del widget. Se llama una sola vez al cargar la página del sitio de la Pyme, inmediatamente después de que el script widget.js se inicializa. Devuelve toda la configuración necesaria para renderizar el banner de cookies: propósitos activos, colores, posición, textos legales y el hash de la política para vincular el consentimiento posterior.

Notas de seguridad
  • La respuesta nunca incluye IDs internos (id, company_id, user_id). Solo datos públicos.
  • No se envía Set-Cookie para no romper el caché de Cloudflare.
  • El widget debe usar el policy_hash recibido al construir el payload del consentimiento.
  • Si la respuesta es 404, el widget no debe renderizar el banner.
POST
Registrar consentimiento
/api/widget/{company_public_uuid}/consent
Propósito / Cuándo se usa

Se invoca cuando el visitante hace clic en Aceptar, Rechazar o Guardar preferencias. El widget envía los fines aceptados como booleans + timestamp + policy_hash. El ledger consent_logs es inmutable. El endpoint es idempotente: reenvíos del mismo payload retornan 200.

POST /api/widget/{company_public_uuid}/consent
Headers requeridos
HeaderValorNotas
Content-Typestringapplication/json Requerido
Acceptstringapplication/json Requerido
OriginstringDominio del sitio. Validado por DynamicCorsMiddleware. Requerido
Path parameters
ParámetroTipoDescripción
company_public_uuidUUID v4Va en la URL para que el middleware CORS resuelva la empresa en preflight OPTIONS (sin body). Requerido
Body params
CampoTipoReglas de validaciónNotas
visitor_uuidUUID v4required, uuidUUID anónimo del visitante. Sin PII.
company_public_uuidUUID v4required, uuid, exists:companies,public_uuidMismo UUID de la URL. Validado en BD.
timestampstring (ISO-8601)required, date_format:Y-m-d\TH:i:s\ZUTC estricto. Ventana: no >5 min futuro, no >1 h pasado.
purposesobjectrequired, array; slugs: sometimes, booleanMapa dinámico según fines activos de /config. necessary_technical se fuerza a true en backend.
El timestamp se valida contra ventana de ±5 min futuro / −1 h pasado (StoreConsentRequest withValidator).

Mismo proof_hash = UNIQUE en BD = 200 con already_recorded. Comportamiento esperado para reenvíos.

  "message": "Consentimiento ya registrado previamente.",
  "data": {
    "status": "already_recorded"
  }

Respuestas de error
CódigoCausaEjemplo de mensaje
403workers_policy u origen CORS no permitido{"status":false,"message":"No se pueden registrar consentimientos de políticas laborales desde el widget.","data":null}
404Empresa sin cookie_policy publicada{"status":false,"message":"Esta empresa no tiene una política de cookies publicada.","data":null}
422Validación: timestamp fuera de ventana, slugs inválidos"El timestamp no puede estar más de 5 minutos en el futuro."
429Rate limit excedido{"message":"Too Many Attempts."}
500Error interno BD (no confundir con duplicado){"status":false,"message":"Error al registrar el consentimiento.","data":null}
Notas de seguridad
  • proof_hash = SHA-256 del payload canonizado (ksort + JSON_UNESCAPED_SLASHES). Determinista.
  • 200 + already_recorded no es error. El widget puede tratarlo como consentimiento exitoso.
  • necessary_technical siempre true en backend, incluso si el cliente envía false.
  • Slugs no activos se ignoran silenciosamente.
  • No exponer proof_hash en URL ni en console.log en producción.

Panel (Angular)

GET
Catálogo de fines legales
/api/panel/consent-purposes
Propósito / Cuándo se usa

Se usa en el panel Angular cuando el usuario llena campos "Otro" con requires_purpose_selection: true en el wizard. Muestra un selector de checkboxes con los fines activos. La selección se guarda en wizard_data[{field_key}_purposes] y el backend los resuelve con WizardPurposeResolverService (regla 3).

GET /api/panel/consent-purposes
Headers requeridos
HeaderValorNotas
Acceptstringapplication/json Requerido
CookiestringSession cookie enviada automáticamente por el navegador. Requiere withCredentials: true en el HttpClient. Requerido
Autenticación: Sanctum cookie-based (SPA). El panel Angular debe haber completado el flujo de login con GET /sanctum/csrf-cookie antes de llamar a este endpoint. Incluir withCredentials: true en todas las llamadas HTTP del panel. No usar Bearer token — las cookies de sesión se envían automáticamente. 
// En app.config.ts o el interceptor HTTP:
provideHttpClient(withFetch(), withInterceptors([...])),
// Y asegurarse de enviar credenciales (o configurarlo globalmente en el interceptor)

Notas de implementación
  • Solo se usa en el panel Angular, no en el widget público.
  • Devuelve todos los fines activos del catálogo global (13 slugs), no solo los que aplican a la empresa.
  • Para el widget, los fines activos se resuelven dinámicamente con WizardPurposeResolverService (3 reglas).
