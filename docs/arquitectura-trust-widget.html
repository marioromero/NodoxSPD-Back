Arquitectura — Captura de Consentimientos

Diagrama de segmentación de políticas, mecanismos de captura y destino final de los consentimientos en el ledger inmutable.

Diagrama 1 — Segmentación de Políticas y Mecanismos

Diagrama 1 — Segmentación de Políticas y Mecanismos

Lógica de Enrutamiento del Sistema

Este diagrama muestra la lógica de enrutamiento completa del sistema: cada tipo de necesidad legal de la Pyme tiene un único camino correcto hacia el registro de consentimiento.

El punto de partida es la plataforma, que distingue tres contextos completamente distintos. Las políticas de cookies operan en el navegador de forma anónima, sin que el usuario haya revelado quién es — para esto existe el Trust Widget, que funciona con un identificador técnico temporal sin PII. Las políticas de privacidad web y los datos de trabajadores, en cambio, involucran identidad real (email, RUT), por lo que se canalizan al Portal Cautivo, donde el usuario firma de forma explícita y vinculante.

El tercer camino (línea punteada) es el Importador Histórico: para Pymes que tienen consentimientos ya obtenidos por otros medios (papel, sistemas antiguos) y necesitan registrarlos sin conectar ninguna API. Este camino desemboca directamente en el ledger, con una marca especial que distingue estos registros de una captura en vivo.

El único destino final para todos los caminos es consent_logs, la tabla inmutable que nunca se modifica ni elimina — solo crece. El paso intermedio pending_consents actúa como sala de espera para el PII que aún no ha sido autorizado por el usuario: existe ahí temporalmente, y desaparece (ya sea porque el usuario firmó y pasó al ledger, o porque expiró y se purgó).

Camino 1: Políticas de Cookies → Trust Widget

Mecanismo A

El usuario navega de forma anónima. El Trust Widget (script JS) se encarga de gestionar el consentimiento de cookies sin necesidad de identificar al usuario. Usa Consent Mode v2 para comunicar las preferencias a Google y otros servicios. No hay PII en ningún momento — solo un identificador técnico temporal.

Camino 2: Privacidad Web / Leads → Portal Cautivo

Mecanismo C

Cuando se capturan datos de contacto (formularios web, leads), el usuario debe firmar la política de privacidad de forma explícita. El Portal Cautivo genera un link único que se envía al email del usuario. Al abrirlo, el usuario revisa y firma electrónicamente, y el consentimiento pasa al ledger. Mientras no firme, los datos residen temporalmente en pending_consents con un TTL de 72 horas.

Camino 3: Trabajadores / RRHH → Portal Cautivo

Mecanismo C

Mismo mecanismo que el Camino 2, pero para datos laborales sensibles. El empleado recibe un link único para firmar la política de privacidad laboral. Al firmar, el registro migra a consent_logs.

Camino 4: Importador Histórico (Bulk)

Bulk Import CSV

Para Pymes que ya tienen consentimientos capturados por fuera del sistema (contratos en papel, sistemas legacy, Google Sheets). El importador procesa archivos CSV y registra los consentimientos directamente en consent_logs con una marca especial que los distingue de capturas en vivo. No pasa por pending_consents porque el consentimiento ya fue obtenido por otro medio.

Destino Final: consent_logs (Ledger Inmutable)

Todos los caminos convergen en consent_logs, una tabla de solo inserción (append-only) que implementa un ledger inmutable. Cada registro incluye un proof hash que permite verificar la integridad del dato. No se permiten actualizaciones ni eliminaciones lógicas — solo crece con cada nuevo consentimiento.

La tabla pending_consents actúa como buffer temporal: almacena PII con un TTL de 72 horas. Si el usuario firma dentro de ese plazo, el registro migra a consent_logs. Si expira, se purga automáticamente.

Notas Técnicas

Trust Widget: El script JS debe cargarse de forma asíncrona y no debe bloquear el renderizado. La comunicación con el backend se realiza a través de un identificador de sesión temporal, sin transmitir PII.
Portal Cautivo: El link único debe incluir un token criptográficamente seguro (JWT con expiración). La firma electrónica se almacena como evento en consent_logs junto con el hash del documento firmado.
Importador Histórico: Cada registro importado debe incluir metadatos de origen (timestamp de importación, fuente, hash del archivo original) para mantener la trazabilidad.
