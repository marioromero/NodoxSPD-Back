API Reference &mdash; Frontend Módulo 2
Trece endpoints para la integración frontend del Trust Widget: configuración del banner, registro de consentimiento, catálogo de fines legales, preview dinámico de fines activos, generación de enlaces de firma (single/batch), sondeo de progreso de lotes, listado de consents pendientes, bóveda de auditoría, gestión de dominios CORS, personalización visual, Portal Cautivo (consulta + firma) y políticas publicadas.


Base URL: https://api.tudominio.com
Formato: JSON &middot; UTF-8
Widget: Público (sin auth) &middot; Panel: Sanctum

Configuración del widget

Propósito / Cuándo se usa

POST

Registrar consentimiento

/api/widget/{company_public_uuid}/consent




Propósito / Cuándo se usa


Se invoca cuando el visitante hace clic en Aceptar, Rechazar o Guardar preferencias. El widget envía los fines aceptados como booleans + timestamp + policy_hash. El ledger consent_logs es inmutable. El endpoint es idempotente: reenvíos del mismo payload retornan 200.





POST
/api/widget/{company_public_uuid}/consent



Headers requeridos


Header	Valor	Notas


Content-Type	string	application/json Requerido

Accept	string	application/json Requerido

Origin	string	Dominio del sitio. Validado por DynamicCorsMiddleware. Requerido






Path parameters


Parámetro	Tipo	Descripción


company_public_uuid	UUID v4	Va en la URL para que el middleware CORS resuelva la empresa en preflight OPTIONS (sin body). Requerido






Body params


Campo	Tipo	Reglas de validación	Notas


visitor_uuid	UUID v4	required, uuid	UUID anónimo del visitante. Sin PII.

company_public_uuid	UUID v4	required, uuid, exists:companies,public_uuid	Mismo UUID de la URL. Validado en BD.

timestamp	string (ISO-8601)	required, date_format:Y-m-d\TH:i:s\Z	UTC estricto. Ventana: no >5 min futuro, no >1 h pasado.

purposes	object	required, array; slugs: sometimes, boolean	Mapa dinámico según fines activos de /config. necessary_technical se fuerza a true en backend.

Respuestas de error


Código	Causa	Ejemplo de mensaje


403	workers_policy u origen CORS no permitido	{"status":false,"message":"No se pueden registrar consentimientos de políticas laborales desde el widget.","data":null}

404	Empresa sin cookie_policy publicada	{"status":false,"message":"Esta empresa no tiene una política de cookies publicada.","data":null}

Notas de seguridad


- proof_hash = SHA-256 del payload canonizado (ksort + JSON_UNESCAPED_SLASHES). Determinista.

- 200 + already_recorded no es error. El widget puede tratarlo como consentimiento exitoso.

- necessary_technical siempre true en backend, incluso si el cliente envía false.

- Slugs no activos se ignoran silenciosamente.

- No exponer proof_hash en URL ni en console.log en producción.

POST

Generar enlace de firma

/api/panel/pending-consents






Propósito / Cuándo se usa


Crea un registro PendingConsent con el email del destinatario cifrado (AES-256-CBC mediante Crypt::encryptString()) y despacha un Job en cola que envía el correo transaccional con la URL mágica del Portal Cautivo. El enlace expira en 7 días. Se usa desde el panel Angular cuando el admin quiere enviar un documento a un trabajador o lead para su firma digital.

Validaciones de seguridad


Regla	Qué valida	Respuesta si falla


Pertenencia	La política (company_policy_id) debe pertenecer a la empresa del usuario autenticado.	403

En modo batch, la deduplicación ocurre asincrónicamente en el Job.	Las inserciones duplicadas se omiten (no fallan).

Respuesta — Modo single (1 email) 201 Created

Si se envía exactamente 1 correo y no existe un pending vigente, se retorna 201 con mode: "single".


{
"status": true,
"message": "Enlace enviado exitosamente.",
"data": {
"mode": "single",
"status": "created",
"message": "Enlace enviado exitosamente."
}
}



200 OK &mdash; Modo single (ya existe vigente)

Si el correo ya tiene un pending activo para esa política, se retorna 200 con status: "already_pending".


{
"status": true,
"message": "Enlace ya enviado previamente, aún vigente.",
"data": {
"mode": "single",
"status": "already_pending",
"message": "Enlace ya enviado previamente, aún vigente."
}
}



202 Accepted &mdash; Modo batch (2+ emails)

Si se envían 2 o más correos, el backend crea un lote (JobBatch) y retorna 202 con el batch_id. La deduplicación y envío ocurren asincrónicamente. No hay sent_count/skipped_count en modo batch.


{
"status": true,
"message": "Lote de 87 correos despachado.",
"data": {
"mode": "batch",
"batch_id": "9c3f...",
"total": 87,
"status": "queued"
}
}
El frontend debe usar batch_id para sondear el progreso vía GET /api/panel/batches/{batch_id} (ver endpoint 12).




Respuestas de error


Código	Causa	Ejemplo de mensaje


401	No autenticado (falta cookie de sesión)	{"status":false,"message":"Unauthenticated.","data":null}

403	Política no pertenece a la empresa o no está publicada	{"status":false,"message":"La política especificada no está disponible para firma.","data":null}

422	Validación: emails vacío, excede 500 o algún email inválido	Errores de validación estándar de Laravel

429	Más de 10 requests POST por minuto (throttle)	{"message":"Too Many Attempts."}






Flujo interno


1Frontend envía POST /panel/pending-consents con array emails + company_policy_id.

&darr;

2Backend valida emails y company_policy_id. Resuelve empresa del usuario autenticado.

&darr;

3Verifica que la política pertenezca a la empresa y esté published. Si no: 403.

&darr;

4Si emails.length === 1: modo single &mdash; verifica duplicados sincrónicamente. Crea PendingConsent y despacha SendConsentLinkJob. Retorna 201 (created) o 200 (already_pending).

&darr;

5Si emails.length >= 2: modo batch &mdash; crea un JobBatch y despacha un Job por email. La deduplicación ocurre async en el Job. Retorna 202 con batch_id.

&darr;

6[Background — Queue Workers] Cada Job descifra el email, verifica duplicados via pii_hash, crea PendingConsent y despacha ConsentLinkMail.



El 201 confirma que al menos un registro se creó y su Job se encoló, no que los correos ya llegaron. El envío es asincrónico vía la cola de base de datos.




Ejemplo de código (servicio Angular)

El input de correo en el modal de "Nuevo Envío" debe permitir múltiples correos (separados por coma o usando un componente de chips/tags). El frontend transforma ese input en un array de strings antes de enviarlo. Si el array tiene 1 email, la respuesta es modo single (201/200). Si tiene 2+, la respuesta es modo batch (202) con batch_id.

sendPortalLinks(emails: string[], companyPolicyId: number): Observable<any> {
return this.http.post(
`${environment.apiUrl}/panel/pending-consents`,
{ emails, company_policy_id: companyPolicyId },
{ observe: 'response' }
);
}

// Manejo de respuesta — discriminar por mode
this.sendPortalLinks(emails, policyId).subscribe({
next: (res) => {
const data = res.body.data;

if (data.mode === 'single') {
// 201 created o 200 already_pending
const msg = data.status === 'created'
? 'Enlace enviado exitosamente'
: 'Enlace ya enviado previamente, aún vigente';
this.showToast(msg);
} else if (data.mode === 'batch') {
// 202 Accepted — sondear progreso con batch_id
this.showToast(`Lote de ${data.total} correos despachado`);
this.pollBatchProgress(data.batch_id);
}
},
error: (err) => this.showToast(err.error?.message || 'Error al enviar')
});

// Sondeo de progreso del lote
pollBatchProgress(batchId: string) {
const poll = setInterval(() => {
this.http.get(`${environment.apiUrl}/panel/batches/${batchId}`)
.subscribe({
next: (res: any) => {
const p = res.data;
if (p.finished) {
clearInterval(poll);
this.showToast(`Lote completado: ${p.processed_jobs}/${p.total_jobs} procesados, ${p.failed_jobs} fallidos`);
}
}
});
}, 3000);
}



Notas de implementación


- Throttle: máximo 10 requests POST por minuto por usuario.

- El company_policy_id debe obtenerse del listado de políticas publicadas (GET /api/company/policies?status=published). Solo políticas publicadas son elegibles.

- El contrato de respuesta depende de la cantidad de emails: 1 correo &rarr; modo single (201/200), 2+ correos &rarr; modo batch (202 con batch_id).

- En modo batch, usar GET /api/panel/batches/{batch_id} para sondear el progreso del lote. No hay sent_count/skipped_count &mdash; la deduplicación ocurre async en el Job.

- Los emails duplicados dentro del mismo array no se procesan dos veces.

- Más detalle en Característica F de la Guía Conceptual.








Panel — Bóveda de Auditoría




GET

Bóveda de auditoría

/api/panel/consent-logs






Propósito / Cuándo se usa


Registro inmutable de toda acción de consentimiento realizada por trabajadores y leads: firma (aceptar/rechazar), expiración automática, revocación. Cada registro incluye un proof hash (SHA-256 de 64 caracteres hex) que encadena cada entrada con su predecesora (previous_hash), formando una cadena de integridad tipo blockchain. Se usa en el panel Angular en la vista "Bóveda de Auditoría" para consulta, exportación y verificación forense.




Inmutabilidad: Los registros en consent_logs no pueden ser modificados ni eliminados, ni por el frontend ni por el backend. Solo lectura (GET). Cualquier intento de DELETE/PUT/PATCH devuelve 405 Method Not Allowed.
